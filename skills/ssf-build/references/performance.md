# 性能问题的测量与取舍

仅用于明确的性能目标、慢请求、卡顿、资源增长或回退；普通实现不加载本参考。沿用既有调试、行为验证和宿主运行约束，不为测量擅自安装、压测生产或启动长期服务。

## 从症状选择证据

先确定用户等待或资源消耗发生在哪里，再选择已有的测量入口；不用通用分数或任意阈值替代项目目标。

| 现象 | 优先区分的原因与证据 |
|---|---|
| 页面首次打开慢 | 网络瀑布与服务端等待、资源体积及阻塞、主线程处理；接口快不代表页面可用快 |
| 点击、滚动或输入卡顿 | 主线程长任务、重复渲染和布局；缩小到实际慢交互，不能仅看接口耗时 |
| 接口或列表慢 | 查询次数及执行计划、外部调用、连接等待、序列化；区分每项重复调用与单次调用慢 |
| 内存或资源持续增长 | 相同旅程重复后的对象、监听器、连接等存活情况；峰值高与无法释放是不同问题 |

把待优化指标与输入规模、账号/权限、版本、缓存状态和环境绑定。历史报告缺少关键条件时只能作为线索，先补可比较基线。区分实际请求、缓存命中与合并等待；一次快样本或冷基线对热结果不足以证明改动收益。

## 只改变已定位的瓶颈

- 重复查询先核对能否批量取数及顺序、重复项、缺失项、租户过滤；索引是否适用要看实际查询计划，不能从“查询慢”直接推出“加索引”。
- 缓存先明确键依赖哪些账号、权限和参数，以及失效与允许陈旧的范围；不能以更快为由改变实时权限、额度等契约。连接池或并发扩大前查清等待原因和下游容量，避免把队列转移到另一层。
- 客户端优化针对测到的资源、计算或渲染成本，不默认添加 memo、缓存或新依赖。减少工作量时确认被省略的工作不是必要校验或业务副作用。

## 决定是否保留

使用相同输入、计时边界、缓存条件和采样方式复测；需要时重复或交错运行前后版本，比较分布及波动，避免把偶然最快值当收益。只有一种状态变快时，明确改善范围及另一状态的代价。

同时核验行为与相关资源成本。将测到的变化与原因对应；查询数减少可证明调用量变化，不能自动证明生产延迟同比下降。无可测收益且增加复杂度的本次候选应移除，只撤回自己引入的内容，不覆盖用户工作；有独立正确性价值的修改单独说明依据。

在现有计划或交付中简记尝试、结果与保留/放弃原因，不另建性能账本。回归保护选与瓶颈相关且稳定的信号，耗时有噪声时不要把一次本机时间写成严格 CI 阈值。
