# 按需调试

采用 mattpocock/skills 的复现反馈、缩小场景、验证假设和回归方法，取消固定阶段审批及固定假设数量。

## 定位第一个偏离预期的位置

建立与用户症状对应的反馈信号：保留脱敏后的关键错误、输入、预期、实际结果和触发次序。优先现有测试、最小请求、CLI fixture 或已有浏览器/设备会话。复现必须捕获原始故障，不能只证明“程序没崩溃”。

找一个相近的正常路径或正常输入，对比配置、权限、数据和版本；近期 diff 是候选线索，不是根因证明。缩小仍能复现的场景，性能问题先取得可比较基线，不擅自对生产施压。

跨组件问题沿边界检查“传入了什么、实际处理了什么、传出了什么”：界面 → 请求 → 服务 → 存储只是示例，按真实链路查证。先确定第一个出现错误值或缺失状态的位置，再向来源回溯。配置文件正确不代表进程实际收到了配置，日志出现调用也不代表外部操作成功。

日志只保留定位所需的状态和脱敏摘要；先区分实际请求、缓存命中和合并等待，避免用重复日志推断重复执行。不打印原始凭据或完整敏感载荷，不借诊断重启用户已有服务。

## 用证据检验假设

在会话中说明当前怀疑的原因、依据，以及什么结果会推翻它。选择能区分竞争解释的最小检查，每次只改变一个关键变量；不能同时改超时、重试与缓存后只凭结果变好就声称找到根因。

假设被推翻后重新定位，不继续叠加补丁。连续尝试没有新增证据，或每次修复都把故障转移到另一处时，检查共享状态、调用顺序或契约是否理解错；停止盲试但继续只读调查。只有新的方案会实质改变范围或业务结果时才询问，不因失败次数自动要求审批或大重构。

异步问题先确认状态属于哪次请求/哪个账号、完成回调是否可能重复或晚到；性能问题确认比较的是相同输入和环境。重试只适用于已确认可重试的失败；吞掉异常、放宽校验或增大等待时间不能替代根因说明。

## 修复并复验

在覆盖实际故障链的公开边界补回归，确认失败来自目标缺陷，再做最小修复。复验原始触发、恢复后的结果和受同一规则影响的正常路径。修复症状所必需的多个位置可以一起改，但应能说明它们对应同一个根因。

清理本次临时插桩，保留项目需要的安全诊断信息。无法复现时区分已证实事实、静态推断和仍缺失的环境信号，继续可行检查；不要把静态修正写成已验证恢复。
