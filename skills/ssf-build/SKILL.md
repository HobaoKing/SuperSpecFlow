# ssf-build

首次采用时简述“使用 ssf-build：用什么方法解决哪个问题、怎样验证”，直接推进；续接不重复播报，用户要求只给结果时省略。只声明实际采用的方法。

从会话、代码和已有计划确认目标。普通多步骤任务不落盘流程文档；跨模块、跨会话或用户要求时维护一份计划，已有计划和指定路径优先，默认 `docs/plans/<topic>.md`。记录目标、边界、任务、验收和进度；可复用 `ssf-plan` 资源，不以另一 skill 不可用为阻塞。

1. 从用户可观察结果确定验收点，定位现有实现、调用方和相关测试。涉及状态或外部操作时沿入口、失败与恢复路径确认约束，并检查受同一规则影响的其他入口；选择最小修改范围，保护无关未提交工作。
2. 外部数据在入口校验并转为约定类型，内部不重复校验。单次简单逻辑内联，一个函数能清楚完成就不拆；异常默认传播，只为实际处理增加窄范围捕获。抽象、异常和推测性加固按 [Karpathy 纪律](references/karpathy.md) 判断；按下表只读适用参考。
3. 本次新增或行为、契约变化的非平凡函数，在实现定义处写简体中文注释，说明功能与实际适用的输入输出语义、约束。涉及业务分支、状态、异步、失败处理或副作用不能豁免；无额外规则的简单 getter/setter、透传、初始化及纯格式调整可豁免，不补写无关历史、生成或第三方代码。
4. 小步实现并验证受影响路径，遵守宿主的构建、运行和设备限制。环境受限时继续可行检查，明确未覆盖范围。验证通过后，只有新改动、失败或具体未决风险才扩大或重跑检查。
5. 检查实际 diff 和 `git diff --check`，核对目标、错误路径及必要注释。已有计划只更新该文件中的任务、验证和剩余事项。
6. 交付变化、原因、验证和限制；缺陷修复给出原信号、修复结果与相关回归，不把静态判断写成运行通过。证据并入正常交付，不另填流程表或宣称未经比较的提升。同范围已授权动作继续；未授权不自动提交或发布。提交时精确暂存并检查实际提交内容，`ssf-git` 可用时复用它。

| 任务信号 | 使用方法 |
|---|---|
| 新功能、跨层改动、接口变化、引入依赖或重构 | [实现策略](references/implementation.md)：先找可复用能力，确认契约，再按行为贯通一小步 |
| 新业务规则、边界条件、适合自动化的缺陷 | [TDD](references/tdd.md)：测试公开行为，确认失败原因，逐项红绿验证 |
| 根因不明、跨组件异常、异步问题、修复反复失败 | [调试](references/diagnosing-bugs.md)：比较正常路径，定位首个失真边界，用可证伪假设推进 |
| 用户可感知的慢、资源增长或性能回退 | [性能](references/performance.md)：按症状取证，定位瓶颈，同条件复测并检查收益与代价 |

已明确根因的一行修复无需完整调研；重构保持现有可观察行为，行为修复与结构调整分别核验。不要靠放宽断言、吞掉异常或增加无依据重试消除失败信号。

仅为推测中的低概率并发或安全边界加复杂度前，先说明故障、概率依据与代码/维护增量，取得用户针对该方案的明确同意；一般修复授权不等于同意额外加固，已有同范围明确授权不重复确认。
