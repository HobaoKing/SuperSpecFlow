# 按需代码审查

采用 mattpocock/skills 从规范和需求两方面检查 diff 的方法，去掉强制 issue tracker、双子 agent 和固定格式依赖。

- 正确性与项目规范：检查条件分支、错误路径、异步生命周期、数据一致性、权限及必要测试。设计坏味道只是线索，必须结合实际代码和宿主约定，不为了抽象而要求重构。
- 需求符合度：以用户会话、已有计划或指定 issue 为依据，检查缺失行为、实现错误和超出范围的修改。不要求独立规格文件或 Spec ID。

## 按影响选检查路径

先将用户要求的行为与当前实现对照，再核对正确性与项目规范。以实际影响排序；不把某个文件类型或风险分类自动等同于高严重性。只审查本次范围相关的信号，避免把清单扩展成无边界的全仓安全审计。

| 变更信号 | 要核实的问题 |
|---|---|
| 数据写入、额度、支付、资源占用 | 校验与写入是否原子；失败会不会丢失/重复数据；事务边界与唯一约束是否真实存在；重试是否重复副作用 |
| 权限、外部输入、第三方或模型结果 | 权限与租户边界由谁执行；输入到命令、查询、URL、文件或渲染前是否按实际信任边界处理，不能只看 UI 校验 |
| 异步、状态机、回调 | 同步和异步终止是否都释放资源；旧请求能否覆盖新状态；重复到达会不会二次执行；超时是否误当明确失败 |
| 枚举、字段、类型、错误语义 | 沿生产者到消费者查存储、过滤、展示、默认分支和历史数据；放宽输入后未修改的调用方是否还能正确处理 |
| 时间、数量、性能 | 单位、时区和时间窗口是否一致；性能担忧是否在真实数据规模下成立；缓存是否改变权限或过期语义 |
| 分发、迁移、配置 | 实际运行版本与配置是否可达；新旧组件能否按发布顺序共存；回退代码能否恢复已有数据 |

## 输出前尝试推翻发现

追踪调用方校验、类型约束、框架错误处理、事务和实际测试。确认问题输入真的可达，保护逻辑没有在另一层完成，当前 diff 没有已经修好它。搜索命中只是线索，读取实际上下文后才能下结论。

例如怀疑失败后没有释放额度，应先看是否由上层统一处理；怀疑新状态遗漏，不只查新增分支，还要读旧过滤器和序列化路径。避免把已有校验之后的“理论空值”、固定小集合的循环或单纯命名偏好当成缺陷。

每个确定发现应能串起：触发条件 → 具体位置 → 违背的契约 → 用户或数据影响 → 支持证据。影响大小与证据确定性分别判断，证据不足标为待核实，不给猜测附高严重性标签。重复根因合并，说明必要的受影响入口；风格建议单独列且不冒充阻塞。

## 收到反馈后再核实

逐项对照真实调用、契约、平台版本和现有保护，判断建议成立、不适用还是仍缺证据；不能因 reviewer 语气确定就照单实施。声称“无用”的分支可能承载旧版本兼容，“统一返回空值”可能吞掉调用方依赖的错误。需要时查历史动机；只在当前授权内修复成立的问题。

反馈不成立时给出反证和影响，不迎合修改。部分反馈不清楚时继续独立可做项，只对实质未决取舍询问，不自动暂停全部工作。修复后回到原触发条件；支撑代码变化时重判旧发现，未变化的有效证据不重复全量评审。
