# ssf-review

先确定审查范围：用户指定的功能、模块、目录、完整仓库、diff、PR 或基线优先。功能或模块审查沿当前实现、调用方与相关测试检查，不因存在无关未提交改动转成 diff 审查，也不要求先有目标分支。只有用户未指定范围时才优先当前未提交改动，其次当前分支相对明确目标分支的差异；需要比较基线却无法可靠确定时再询问。审查请求本身不授权修复，已另行授权的修复除外。

按 [审查参考](references/code-review.md) 检查两方面：代码正确性与项目规范、是否满足会话或已有计划的需求。核查是否遵守 Karpathy 纪律（无过度设计、无无关修改），本次新增或行为、契约变化的非平凡函数，其实现定义处是否有准确的简体中文函数级注释；业务分支、状态、异步、失败处理和副作用不能豁免，无额外规则的简单 getter/setter、透传、初始化或纯格式调整可豁免。不扫描补写无关历史、生成或第三方代码。缺少独立规格文件不阻塞审查。

给出可定位的文件、行号、触发条件、影响和建议；把事实缺陷与风格偏好分开。没有发现问题时直接说明检查范围和剩余验证缺口，不凑问题数量。

默认本会话检查，不强制 issue tracker 或并行子 agent。用户要求独立核验时，给 reviewer 足够的需求、diff 和真实验证证据；不得把自己的检查称为独立审查。收到反馈后先复现或核实，再在授权范围内修复。

通常在会话中输出；跨会话需要记录时补到已有计划，不要求多份 request/evidence/signoff 文件。
