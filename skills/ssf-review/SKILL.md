# ssf-review

首次采用时用一句话说明使用 ssf-review、审查范围与关注的风险；续接不重复播报，用户要求只给结果时省略。

先确定审查范围：用户指定的功能、模块、目录、完整仓库、diff、PR 或基线优先。功能或模块审查沿当前实现、调用方与相关测试检查，不因存在无关未提交改动转成 diff 审查，也不要求先有目标分支。只有用户未指定范围时才优先当前未提交改动，其次当前分支相对明确目标分支的差异；需要比较基线却无法可靠确定时再询问。审查请求本身不授权修复，已另行授权的修复除外。

按 [审查参考](references/code-review.md) 沿需求、入口、共享规则及失败/恢复链核查正确性，再反证候选发现；缺少独立规格文件不阻塞。只读适用参考，复用未变化的有效证据。

核查简单、精准修改与项目规范。本次新增或行为、契约变化的非平凡函数，检查实现定义处的简体中文注释是否准确覆盖规则、状态、异步、失败处理或副作用；简单无额外规则的 getter/setter、透传、初始化及纯格式调整可豁免，不扩大到无关历史、生成或第三方代码。

交付先给已核实的发现，包含严重程度、文件行号、触发条件、影响、证据和建议，再给覆盖范围与验证缺口。疑点和风格偏好不冒充事实缺陷；相同根因合并，无发现时直说，不凑数量或输出无依据评分。

默认在本会话检查，不强制 issue tracker 或子 agent。获准独立核验时提供需求、范围和真实证据，不把自审称为独立审查。收到反馈按参考核实，不能直接照单修改。

通常在会话中输出；跨会话需要记录时补到已有计划，不要求多份 request/evidence/signoff 文件。
