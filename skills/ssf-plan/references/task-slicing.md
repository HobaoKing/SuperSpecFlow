# 按交付结果拆分任务

用于跨层功能、契约变化、迁移或仍有关键未知的计划。用现有规则和代码填实任务；不要求固定任务数量、时长或行数。

## 先确定依赖和未知

定位用户入口、数据/状态归属、对外契约、调用方与现有验证方式。写清楚已找到的相关路径；尚未定位时把定位作为明确任务，不捏造文件名或接口。复用已决事项，仅保留会改变后续方案的未知。

会导致方案整体失败的未知先做最小验证；例如先确认目标环境支持所需能力，再写依赖它的整套功能。验证应有明确问题、可接受证据与结束条件，不扩成无限调研。

## 一步交付一个可观察行为

- 优先将必要的接口、实现、界面和测试组织成贯通的一步，完成后能证明一个行为；避免“先写所有表，再写所有 API，最后做所有页面”直到末尾才发现契约冲突。
- 如果必须按层推进，先明确共享契约及集成检查；mock 通过仍要保留真实集成的验收任务。
- 将必要的配置、文档与测试放到它所支撑的任务中。结构重构和业务行为变化分开核验，但不为此自动拆分提交或建分支。
- 每个任务说明交付行为、相关位置、前置依赖和验收。验收写预期结果与可用检查方式，不能只写“测试通过”。涉及失败处理时给出关键失败及恢复结果。

例如“失败后允许重试上传”可拆为：明确失败/成功契约和额度归属；完成上传失败释放与再次成功的贯通路径；核验重复响应和另一上传入口的回归。文件改得再少，只要业务链不闭合，就不算该任务完成。

## 在执行前消除计划自身的缺陷

对照原始需求，检查每项必要行为是否有任务，任务是否引入了用户没要求的能力，后续步骤的字段、状态、单位是否与前面一致。关注半完成状态：旧调用方会看到什么、迁移如何衔接、失败后停在哪里。

计划应足够具体，让下一位执行者无需重新决定业务语义；不要粘贴整份未来实现。执行发现前提错误时修正当前计划中受影响任务，保留仍有效的结果，不重复建计划或重新申请同范围授权。
