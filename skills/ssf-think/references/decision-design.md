# 从问题到可执行方案

用于产品方向、架构取舍和仍有实质不确定性的需求。目标是做出有依据的决定，分析深度随风险调整；明确的小任务不必逐项展开。

## 确认真正要改变的结果

从用户描述和现有实现中找出：谁在什么场景遇到什么问题，现在如何完成，什么可观察变化算改善。将事实、用户约束和 agent 推断分开；推断可以用于推进可逆工作，但不能写成用户已确认。

用户提出的技术方案也是待判断的手段。例如“加一层缓存”背后的目标可能是减少重复请求；先看是否已有缓存、请求合并或不必要刷新，再比较方案。用户已明确指定技术路线时，在其范围内完善，不擅自换题。

## 按领域顶级专家的实际方法推进

在原任务范围内加深判断，按相关性处理以下问题；由 agent 调查和执行，不变成要求用户逐题作答的访谈：

- 专家会补查什么：识别会改变决策的遗漏、反例或关键约束，说明具体影响；不靠“专家认为”或术语堆砌替代依据。
- 从什么原始材料开始：按下节追到能支撑当前判断的最接近事实的材料，核对来源、口径与缺失，不把摘要当事实。
- 用什么专业方法：按下节选能区分关键假设的方法并实际执行，保留输入、操作与结果，不以工具名字代替调查。
- 谁或什么能作外部判据：优先查找与本任务直接相关的第三方标准及测试向量、独立维护的参考实现或校验工具；需要专业判断时说明可由哪个外部专家或机构核验。选定依据后，在授权范围内实际核验并报告原始结果，不能只列工具名字或未来计划。

说明外部依据的来源、版本或日期及能证明的具体结论。标准文本可支持规则解释，只有实际运行工具或取得评审结果才能声称已验证；通用编译、格式校验不能证明业务正确。自写测试、自己编写的检查器或另一个 AI 的赞同可作内部证据，不能冒充第三方背书。没有适用工具或未取得外部复核时明确写出缺口与可执行的下一步；联系他人、付费或外传资料按实际授权处理。

## 从原始材料建立依据

围绕会改变决策的主张追溯来源：需求看原始场景和有效约定，故障看实际请求、响应、日志与代码，指标看明细及采集定义，能力限制看对应版本的官方契约。先用已有授权材料，只取足以判断的范围，不要求每次收集所有类别。

实际打开关键材料，核对会影响结论的版本/时间、样本范围、单位、统计分母与采集方式。原始数据也可能重复、缺失、偏采或记录失败；抽查摘要怎样由明细得出，必要时重新计算。记录关键筛选、去重或换算，不能靠静默丢弃异常样本得出漂亮结论。

材料冲突时先查适用条件和生成过程，区分观察事实与解释；原始材料无法取得时标明缺口及受影响结论，不把摘要、演示数据或推测补成已核实事实。只在证据足以支撑当前决定时收敛，不无边界搜集。

## 将专业方法变成实际操作

先明确要区分的假设或取舍、什么观察会改变建议，再选择最小足够的方法：性能用同条件测量与瓶颈分解，状态问题用迁移/调用链与反例，兼容性用对应版本契约及真实边界输入，产品判断用原始场景与代表性样本。不能仅因熟悉某个框架就套用，也不凭样本计数或工具通过推断因果。

优先复用现有工具；工具决定结果时核对其版本、参数和适用限制。执行可行的查询、复现或实验，按问题选必要的基线、负向样本或对照，避免不同环境、版本或样本混比。验证仍遵守当前任务授权；无法执行时说明原因和验证办法，只能称拟采用方法。

保留足以复核的材料位置、关键命令/查询或操作、实际结果与解释；用已有会话或计划承载，不另造报告体系。区分工具原始输出、由此得出的推断和未覆盖范围；证据支持的结论有限就缩小建议，不为显得专业扩大实现。

## 业务含义不一致时

仅当术语含糊、同名概念跨模块含义不同，或需求与代码冲突时，核对现有 PRD、计划、术语说明和实际行为；区分当前约定、历史兼容与待修缺陷，不能默认最新代码就代表正确业务。用一个会改变结果的边界场景检验含义，例如“取消已支付订单是否同时退款”，而不是只统一名称。

能够从当前会话和有效约定确定时直接采用；只有互相冲突且无法可靠推断的业务取舍才询问。已确认的含义复用原有计划或契约，仅在需要跨会话保留时更新；不默认新建术语表或 ADR，也不把完整领域建模加到小任务上。

## 检验能推翻方案的前提

- 不做改变的真实代价是什么？用当前故障、工作量或限制说明，避免为假想需求扩张范围。
- 哪个假设一旦不成立，推荐方案就不值得做？如 SDK 不支持、真实瓶颈不在这里、用户入口根本到不了该流程。
- 先用现有代码、版本化接口、最小请求或本地样例检查该假设。普通只读检查直接做；需付费、外传或改变共享环境时遵守已有授权边界。
- 信息不足时说明不确定性及其影响，提出最能消除该不确定性的问题；不用一串通用访谈问题替代调查。

## 比较真实可选的方案

将最小有效改变作为比较基准；只有存在有意义的替代方案时才并列比较。比较维度取决于目标：用户收益、复用的现有能力、维护与迁移成本、最坏失败后果、能否恢复。不要编造精确工期、评分或收益百分比。

给出推荐及其依据，同时说明什么新证据会改变推荐。若两种选择实质改变业务、费用或外部契约且无法由现有约定判断，交由用户决定；普通实现选择自主处理，不把每个前提变成审批。

若准备为仅推测、低概率的并发或安全边界增加复杂度，先列具体故障和触发条件、概率及证据、预计新增代码/状态与维护成本，并比较简单方案；概率无依据就写未知。取得用户针对该方案的明确同意后才增加，已有同范围明确授权可复用；没有价值的加固直接不做，不用“理论更稳”作为实施理由。

## 形成能交给实现的结论

结论将关键建议对应到原始材料、实际采用的方法及判据，说明目标行为、必要边界、取舍、成功和关键失败场景，以及仍未证实的前提。沿用现有计划或会话，不为了讨论再造规格体系。探索性样例只证明被测试的假设，不直接作为生产方案已验收的证据。
